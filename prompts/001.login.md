════════════════════════════════════════════════════════════
▛▞// LAW :: First Principles
The build holds to every law here. Break one and the build is
wrong, no matter how good the rest looks.

▛/// Real Or Empty
Every value on screen is a real value, or an empty state that
says it is empty. No placeholder product, no sample sale, no
chart drawn from invented numbers. A screen of fake data is
worse than a blank one, because it lies about what exists.

▛/// Telegram Is Identity
The only way a person becomes known to TPR is Telegram's own
signature. No password field, no email capture, no Google or
Apple button, no signup form anywhere. Telegram already proved
who they are; TPR only checks that proof.

▛/// The Token Stays Secret
The bot token lives in Base44 project secrets, read only by the
server-side auth function. It is never printed, logged, embedded
in client code, or returned in a response. Same for raw initData.

▛/// The Login Is The Whole Scope
This piece builds the login and the empty shell behind it, and
nothing else. No relay logic, no routing, no settings, no
billing. When the login works and the shell renders, it is done.
:: ∎

▛▞// DESIGN :: The War-Room Look
The whole app wears one skin, fixed here so the build cannot
drift into its own taste. Dark ledger, built for a phone first.
Baseline image at Marduk/station/tpr/battle-log.png — study it
before drawing a screen, never compose the layout from memory.

    delivered #58D6A9     refused   #E4574F

▛▞ Type And Space
Numbers are large and confident and carry the color; prose stays
quiet and gray. Gold marks the one thing that matters on a

▛▞ Motion And Fit
Motion is near-none: things appear, they do not slide or bounce.
No spinner ever turns; a wait shows a single quiet word. Every
screen is built mobile-first and stays whole on a phone held in
one hand, because that is where this lives, inside Telegram.

yields :: a battle report, not a dashboard.
:: ∎

════════════════════════════════════════════════════════════
▛▞// THE DOOR :: Before Login
The screen a person sees before they are logged in, and the only
way in. On load, the page reads window.Telegram.WebApp.initData
and POSTs it to the server function auth.

▛▞ Opened In Telegram
While the check runs, the screen shows one quiet line, "checking
signature", and nothing that spins or flashes. On success the
screen moves to The Shell in one clean cut, no animation. If a
live session already exists from a recent open, the check is
skipped and The Shell shows at once, so a returning person never
waits on a door they already walked through.

▛▞ When The Check Fails
A bad or expired signature does not fail silently. The screen
shows one card, "This link could not be verified. Open TPR again
from Telegram.", with the same gold button to
https://t.me/tpr_zenbot. It never shows a raw error, a code, or
a stack. The person always has one clear way forward.

▛▞ Opened Anywhere Else
There is no initData to read. The screen shows one centered card
reading "TelePromptR opens from Telegram", with a single gold
button linking to https://t.me/tpr_zenbot, and nothing else. No
login form is ever rendered as a fallback.

yields :: a door only Telegram can open.
:: ∎

════════════════════════════════════════════════════════════
▛▞// THE SHELL :: After Login
The first screen a logged-in person lands on. It is the
battle-log shell, empty today and honest about being empty.
Three zones, the same bones as the baseline image.

▛▞ The Top Bar
Two running totals, right-aligned: "relayed 0" and "spent 0".
True counts. They read zero today because zero is the truth, not
because a number is missing.

▛▞ The Shape (Left)
The session as plain rows, in this order: the person's name;
their Telegram id, with a copy button beside it the way a Game
ID has one; the time they signed in, shown plainly as a date and
time, not a raw timestamp; and the bot they talk to, @tpr_zenbot.
Tapping the copy button copies the id and the button briefly
reads "copied", then returns. Log out sits small at the foot and
returns the person to The Door.

▛▞ The Relay Log (Right)
One designed empty state: "No relays yet. Add TPR to a group and
speak." No fake cards, no grayed-out examples, no chart
flatlined at zero. This panel is built to hold relay cards in a
later piece; today it holds only its empty state, and it says so
rather than pretending a card will appear.

yields :: the battle-log shell, honest at zero, ready to fill.
:: ∎

════════════════════════════════════════════════════════════
▛▞// THE CHECK :: fn auth
The server function that makes the login real. It verifies
Telegram's signature over initData, exactly as Telegram
specifies, with no shortcut taken.

▛▞ The Steps
    1  parse initData as a querystring, and pull out hash
    2  data_check_string = every remaining field as k=v, sorted
       by key, joined with a newline
    3  secret   = HMAC_SHA256("WebAppData", TELEGRAM_BOT_TOKEN)
    4  expected = hex HMAC_SHA256(secret, data_check_string)
    5  compare expected against hash in constant time; a
       mismatch is a rejection
    6  reject also if auth_date is missing, older than 3600
       seconds, or in the future; reject if there is no user
    7  on success, upsert a User by telegram_id, start a
       session, and return who the person is

▛▞ The Session
On success the server sets a session that lasts a bounded time,
so a returning person inside that window lands straight on The
Shell without re-checking. When the session lapses, the next
open runs the full check again. The session never outlives the
person's own Telegram session.

▛▞ First Time And Every Time
The first time a telegram_id is seen, a User row is created. On
every open after, that same row is found and its last_seen is
updated. One person is one row, forever; a second login is never
a second account.

▛▞ On Rejection
Return a plain reason for the client to show its card, and log
nothing sensitive: not the token, not the initData, not the
failing hash.

yields :: identity proven by signature, never by claim.
:: ∎

════════════════════════════════════════════════════════════
▛▞// THE RECORD :: One Entity
Login needs exactly one table, the smallest that can hold a
signed-in person. It is created here and nothing else is.

    User :: telegram_id (unique) · username · first_name ·
            created_at · last_seen

telegram_id is the key and never changes. username and
first_name are copied from what Telegram signed, and refreshed
on each open in case the person changed them. created_at is set
once; last_seen moves every visit. No email, no password hash,
no role — none of it exists because none of it is needed to know
who someone is.

yields :: one row per real Telegram person, nothing more.
:: ∎
